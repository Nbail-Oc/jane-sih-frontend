# Dark Web Threat Actor Attribution Dashboard – Research Findings

**STIX 2.1** (Structured Threat Information eXpression) is an OASIS standard JSON-based language for cyber threat intelligence.  It defines a set of *STIX Domain Objects* (SDOs) – e.g. **Threat Actor**, **Intrusion Set**, **Campaign**, **Indicator**, **Malware**, **Tool**, **Infrastructure**, **Identity**, etc. – each with specific properties.  It also provides *STIX Relationship Objects* (SROs) – notably **Relationship** (linking any two objects with a verb, e.g. “*Actor A uses Malware X*”) and **Sighting** (recording that an observable was seen).  In practice, STIX lets analysts model threat data as a graph of interconnected objects.  

We can adapt this model without full STIX compliance.  For example, we could map our actor profiles to STIX *Threat Actor* objects, use *Identity* for personal attributes, and represent things like hidden services or infrastructure nodes using the *Infrastructure* or *Observed-Data* objects.  Handles, PGP keys or blockchain addresses could be captured as **Indicators** (STIX supports patterns for domains, hashes, etc.) or as *Cyber-observable Objects*.  We would then link these with STIX *Relationship* objects (e.g. Threat Actor *“uses”* Indicator).  Even if not outputting full STIX bundles, using STIX’s data model as a guide ensures interoperability: e.g. each object has a unique ID and standard fields like “confidence” and timestamps.  In summary, STIX 2.1 provides a rich ontology of CTI concepts (Threat Actor, Indicator, Tool, Relationship, Sighting, etc.) that can serve as a blueprint for our schema.

**Confidence scores in existing platforms:**  OpenCTI, Maltego and MISP each handle confidence in their own way, but none appear to use a complex fusion algorithm by default.  In OpenCTI, “confidence” is a numeric value (typically 0–100) that analysts or connector users assign to each object (e.g. an Indicator or Threat Actor).  This scale can be customized (e.g. using NATO/admiralty codes).  OpenCTI does not automatically combine multiple signals into a score – the connector or user simply sets the confidence for each entity.  Maltego itself does not calculate scores; instead, users or transforms can attach custom properties to links.  For example, a transform can add a `MaltegoLinkProperty` named “confidence” with a value (e.g. 0.95) on a link between two entities.  In other words, Maltego edges *can* carry a confidence or weight, but any aggregation of evidence must be done externally (it provides no built-in probabilistic fusion).  

MISP offers a more structured approach: analysts can tag data with taxonomies (e.g. “source reliability” or “information credibility”) and also use the **Opinion** field, which is an explicit 0–100 confidence/agreement score attached to any object.  In addition, MISP supports *Sightings* (reports of seeing an indicator) that can boost confidence.  Academic work on MISP has proposed combining taxonomy tags and source reliability into a “base score” for indicators: essentially a weighted sum of tag scores plus a source-confidence factor.  This base score (0–100) then decays over time unless refreshed by sightings.  In summary, MISP’s method is a weighted tagging scheme (noisy-OR is not built-in), OpenCTI uses flat user-defined 0–100 scores, and Maltego allows arbitrary weights on edges.  None of these systems report using complex fusion algorithms; they rely on analyst-input scores or simple arithmetic of tag weights.

**Web Graph Visualization Libraries:**  For an interactive dashboard, several open-source JS libraries are viable.  **Cytoscape.js** is a rich toolkit (canvas/SVG) focused on graph analysis and layouts.  It includes many built-in algorithms (shortest-path, centrality, clustering, various layouts) and styling options, making it ideal when analysis features are needed.  Its drawback is performance on very large graphs – complex layouts can block the UI thread.  **Vis-network** (from vis.js) is optimized for interactive network diagrams with physics simulation, drag/drop and clustering.  It makes it easy to let users move nodes around and supports dynamic updates, but it uses Canvas and can struggle if the physics solver is forced to render too many nodes.  **Sigma.js** is a WebGL-based renderer (with a “graphology” data model) designed for very large/dense graphs.  It achieves high rendering speed for tens of thousands of nodes, but exposes far fewer built-in algorithms and requires more custom code for things like layout or labeling.  (Another option is **D3.js** with force layouts, but D3 is low-level: you’d need to code most graph features yourself and it doesn’t scale as easily as the others for networks.)  In brief: Cytoscape.js is best for small-to-medium graphs with heavy analysis needs; vis-network is best for moderate-sized, highly interactive/physical layouts; Sigma.js excels on very large graphs where raw performance (WebGL) is the priority.

| Library       | Renderer  | Best for                    | Pros / Cons (tradeoffs)                                                       |
|---------------|-----------|-----------------------------|--------------------------------------------------------------------------------|
| **Cytoscape.js**  | Canvas/SVG | Analysis-heavy graphs       | Rich API (algorithms, layouts, styles), graph-theoretic features; can be CPU-bound on large graphs. |
| **vis-network**   | Canvas    | Interactive networks       | Built-in physics, clustering, user-editing of nodes/edges; very easy to use and update dynamically; may lag if graph is very large or physics enabled. |
| **Sigma.js**      | WebGL     | Large-scale graph rendering | High-performance with WebGL (handles thousands of nodes); minimal built-in analysis (requires additional libraries), more setup work. |

**CSV/JSON Export Best Practices:**  Intelligence exports should include both the raw data fields and metadata for context.  Common fields include a unique ID and type, the observable value or pattern, and any descriptive text.  For indicators, include *confidence* and *provenance* columns.  For example, Microsoft Sentinel’s CSV template includes columns like `confidence` (0–100), `tlpLevel` (Traffic Light Protocol marking), and `tags` along with the indicator value.  It also requires a `SourceSystem` or source field that stamps the origin of each indicator.  JSON exports typically follow a STIX-like schema: for an Indicator this means fields such as `"pattern"`, `"pattern_type"`, `"name"`, plus metadata like `"valid_from"`, `"confidence"`, and any marking (`"object_marking_refs"`) for TLP.  In general, ensure exports capture: 

- **Identifier and Type:** unique ID and object type (Indicator, Threat Actor, etc.) for traceability.  
- **Technical Data:** the observable value or IOC (e.g. domain, IP, wallet address) or STIX pattern.  
- **Attributes:** description, category/type, kill-chain phase or tags/labels.  
- **Time/Validity:** creation and observation dates, `valid_from`/`valid_until` fields.  
- **Confidence:** a numeric score column or JSON field (e.g. `"confidence":95`).  
- **Provenance:** source system or author (Sentinel’s `SourceSystem`), and any markings.  In CSV one might include a `tlp` or `sharing` column; in STIX JSON this is done via `object_marking_refs` to TLP definitions.  

Each row (in CSV) or object (in JSON) should thus convey not just the indicator itself but how trustworthy it is (`confidence`, tags) and where it came from (`source`, dates, marking).  This makes the exported data immediately usable for analysis or reporting and preserves the needed context.
